# CNC Sorting → Allocation — Fixed Integration

## Authoritative data flow

```text
Sorting Dashboard
      ↓
POST /submit
      ↓
Sorted rows are returned in the exact sorting order
      ↓
[ Proceed for Allocation ]
      ↓
POST http://localhost:8001/allocate
{ "rows": sortedRows }
      ↓
Allocation Engine consumes row 1 → row 2 → row 3 → ...
      ↓
Primary / Alternative machine selection
      ↓
Per-machine queue
      ↓
Stage 1 → Stage 2 dependency
      ↓
allocation_result (MySQL)
      ↓
GET /allocation-results
      ↓
Allocation Dashboard
```

## Important design rule

The Allocation API **does not sort the rows**. The order received from the Sorting Dashboard is authoritative.

Every click on **Proceed for Allocation** starts a fresh allocation run:

1. Reset the in-memory machine queues.
2. Delete old rows from `allocation_result`.
3. Process the newly supplied sorted rows from first to last.
4. Save only the new allocation result.
5. Redirect to the Allocation Dashboard.

Therefore a new Sorting submission produces a new allocation schedule.

## Database roles

### `testdata3`
Production/master data used by Sorting. It contains the machine alternatives and SMH values required by Allocation.

### `allocation_result`
Output table generated by the Allocation API.

### `testdata_fina`
Legacy/old flattened data table. The new integrated Allocation flow does **not** use it.

## Machine rules

For each stage:

1. Primary and alternative are alternatives, not simultaneous machines.
2. If both are free, primary wins.
3. If primary is busy and alternative is free, alternative is used.
4. If both are busy, the machine with the earliest available time is selected.
5. If availability is tied, primary wins.
6. A machine's queue end is updated immediately after each allocated stage.
7. Stage 2 cannot start before Stage 1 of the same part finishes.
8. The same machine cannot have overlapping jobs.

## XAMPP / phpMyAdmin

1. Start **Apache** and **MySQL** in XAMPP.
2. Open phpMyAdmin.
3. Make sure database `cnc_job_scheduler` exists.
4. Make sure `testdata3` exists and contains the machine columns.
5. Make sure `allocation_result` exists. The Allocation API also creates it if missing.
6. Run `api/allocation_integration.sql` if you want to verify/create the output table.

The previous `testdata_final` table is not required by the new flow.

## Run the APIs

From the project root:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r api\requirements.txt
```

Terminal 1 — Sorting API:

```powershell
python -m uvicorn sorting.main:app --reload --port 8000
```

Terminal 2 — Allocation API:

```powershell
python -m uvicorn api.main1:app --reload --port 8001
```

Then open `sorting/index.html`.

## Manual verification

After sorting:

```text
Proceed for Allocation
```

The browser should call:

```text
POST http://localhost:8001/allocate
```

The request body must contain:

```json
{
  "rows": [
    {
      "priority": 1,
      "project": "maruti",
      "module": "door",
      "ac_comp": 5,
      "extra_data": {
        "SR": 1,
        "PART_NO": "b1.12.58.46",
        "machine_STAGE1": "DMG1",
        "machine_STAGE1_A": "DMG2",
        "STAGE1_smh": 3,
        "machine_STAGE2": "EMCO",
        "machine_STAGE2_A": "FEMCO",
        "STAGE2_smh": 2
      }
    }
  ]
}
```

Then verify:

```text
GET http://localhost:8001/allocation-results
```

and in phpMyAdmin:

```sql
SELECT *
FROM allocation_result
ORDER BY id ASC;
```

The `id` order is the allocation processing order for that run. Machine queue positions are stored separately in `stage1_queue_position` and `stage2_queue_position`.
